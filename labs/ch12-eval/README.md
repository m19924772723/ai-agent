# labs/ch12-eval —— 评测集 + LLM-as-judge 一致性对比（U9 单元）

## 1. 出处

- 母本：第 12 章《智能体性能评估》—— 12.1 评估基础（12.1.1 为何需要评估 / 12.1.2 主流基准）、12.4 数据生成与 LLM Judge
- 参考代码：`code/chapter12/08_data_generation_llm_judge.py`（框架 `hello_agents.evaluation.LLMJudge` 的用法）
- **本 lab 不依赖框架**：用裸 SDK 自己写打分器，原因是本单元要比的是"两套打分器的一致性"，要用同一份预测结果喂给两者，框架的 LLMJudge 是"从问题生成答案再打分"，形态对不上。

## 2. 设计（延续 U6 的"真值判分"纪律，但升级成正式评测）

| 部分 | 做法 |
|---|---|
| **评测集** | `make_dataset.py` 生成 `dataset.json`：20 条用户反馈，每条带人工真值（类型/严重度/模块）+ 4 条**边界样本**（模糊表达） |
| **冻结口径** | 三处必须同源：数据标注、抽取提示词、裁判评分标准——都来自同一个 `RUBRIC_TEXT` 常量 |
| **真值自检** | `self_check()` 由代码校验格式与分布（U7 教训：判据本身会错，不能手写信任） |
| **抽取** | 20 条反馈 → 结构化 JSON，结果缓存进 `out/predictions.json`（重跑不重复花钱） |
| **打分器 A** | 规则判分：逐字段精确匹配（口径是闭集，这是最客观的基线） |
| **打分器 B** | LLM-as-judge：把「原文 + 预测 + 真值 + 口径」给裁判模型，逐字段判一致性并给理由 |
| **反向探针** | `probe_judge.py`：**故意注入 3 条错误预测**，验证裁判是真的在比对，而不是只会点头 |

> 为什么要反向探针：主实验里两套打分器 **100% 一致**。"一致"有两种解释——都准，或裁判没意见。不把后者排除掉，这个"一致率"就是无效数字。

## 4. 真实输出（2026-10-06 实测，step-3.7-flash）

**① 评测集**：20 条（边界样本 4 条），自检通过
分布：类型 bug 8 / 体验 7 / 需求 5｜严重度 高 4 / 中 10 / 低 6｜模块 支付 4 / 列表 3 / 登录 3 / 搜索 3 / 内容 4 / 其他 3

**② 主实验：规则判分 vs LLM 裁判**

| | 全对条数 | 类型 | 严重度 | 模块 |
|---|---|---|---|---|
| 规则判分 | 15/20 | 19/20 | 17/20 | 18/20 |
| LLM 裁判 | 15/20 | 19/20 | 17/20 | 18/20 |

**一致率 20/20 = 100%**｜严格性差异：规则更严 0 条、裁判更严 0 条｜tokens：抽取 8568 + 裁判 15699 = **24267**

**③ 反向探针（关键验证）**：注入 3 条错误预测 → **规则 3/3 抓到、裁判 3/3 抓到**（裁判本轮 tokens 15113、解析失败 0）

| 注入 | 改成 | 裁判抓到 | 裁判给的理由（摘要） |
|---|---|---|---|
| S01 严重度 高→中 | 中 | ✅ | "涉及扣款后订单未生成，涉及资金与数据异常，按口径应为高" |
| S05 类型 需求→体验 | 体验 | ✅ | "希望新增搜索按时间排序的能力，属于需求类" |
| S07 模块 内容→其他 | 其他 | ✅ | "详情页白屏属于内容模块范畴" |

**④ 模型错在哪（5 条 / 20 条）**

| id | 反馈摘要 | 预测错在 | 真值 → 预测 |
|---|---|---|---|
| S07 | 打开详情页白屏，刷新三次才好 | 严重度 | 中 → **高** |
| S11 | 支付成功后没收到通知，客服入口也找不到 | 类型 + 严重度 | 体验/中 → **bug/高** |
| S12 | 建议把常用功能放到首页 | 模块 | 内容 → **其他** |
| S18 | 登录后偶尔会自动退出 | 严重度 | 高 → **中** |
| S20 | 提交评价时一直转圈，最后提示保存失败 | 模块 | 其他 → **内容** |

**边界样本（S13–S16）全部 3/3 答对**——说明这 4 条"我觉得模糊"的样本，在冻结口径下其实不模糊（见结论 3）。

## 5. 结论

1. **"一致率 100%"必须先被证伪再采信**：主实验两套打分器完全一致，靠反向探针（注入 3 条错误、检出 3/3）才能说"裁判确实在比对"。**任何一致性指标都应配一个"故意做错"的对照组**——这是本单元最有价值的方法论。
2. **两套打分器在同一口径下几乎等价，但成本差一个数量级**：规则判分 0 token、毫秒级；裁判每轮 15699 token、约 70 s。**所以**闭集字段的评测优先用规则判分，LLM-as-judge 留给"规则写不出来"的场景（开放答案、语义等价、理由质量）。
3. **我以为的"边界样本"其实不边界**：S13–S16 被模型全对。真正的分歧点是 S11（"没收到通知"算 bug 还是体验）、S07/S18/S20（严重度与模块的边界）——**所以**口径的难点不在"模糊表达"，而在"跨类别表达"（一条反馈同时具备两类特征）。下一版评测集应按"跨类别"设计，而不是按"语焉不详"设计。
4. **模型在严重度上最不稳（17/20）**：4 个错误里有 3 个涉及严重度，且方向相反（S07 判重、S18 判轻）——**所以**严重度维度需要更细的分级说明或示例锚点（few-shot），而不是继续调提示词的措辞。
5. **评测成本要预算**：20 条样本一次完整评测 ≈ 24k token；若按阶段2 每周跑一次、每次改提示词都跑，评测集扩到 100 条就是 ~120k token/次。**所以**"改完先跑子集（10 条）+ 定期跑全量"是必要纪律。
