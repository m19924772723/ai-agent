# labs/ch04-paradigms —— 三种经典范式同题对照（U6 单元）

## 1. 出处

- 母本：第 4 章 **4.2 ReAct / 4.3 Plan-and-Solve / 4.4 Reflection**（只对结构，代码自写）
- 参考文件：`code/chapter4/ReAct.py`、`Plan_and_solve.py`、`Reflection.py`

## 2. 改了什么 / 为什么

| 项 | 母本 | 这里 | 为什么 |
|---|---|---|---|
| 目的 | 三个范式各演示一遍 | **同一道题、同一批工具**跑三条路线，客观判分 | 要的是"适用场景 / 成本 / 失败模式"的可比数据，不是三个孤立的 demo |
| 判分 | 人工看输出 | 脚本用**真值**检查最终答案里是否出现正确条数与类别词 | 把"好不好"变成布尔值，避免自我感觉良好 |
| 工具 | 搜索 + 计算 | `count(kw)`（支持多关键词 OR）+ `all()`（本地确定性） | 反馈统计题只需要"数数"，去掉外部依赖后差异全来自控制流 |
| 留档 | — | v1（工具口径 bug）/ v2（修好）两轮证据都留 | 第一轮三条路线全挂，原因在**工具设计**不在范式，必须留证 |

## 4. 真实输出（2026-10-03 实测，step-3.7-flash）

**v2（工具修好之后）**

| 范式 | 步数 | 工具调用 | token | 耗时 | 判分 | 最终答案（摘要） |
|---|---|---|---|---|---|---|
| plan-and-solve | 3 | 2 | **6810** | 34.8 s | ❌ | "性能卡顿类，**共 5 条**"（把"白屏"也算进卡顿） |
| react | 3 | 2 | **2959** | **16.5 s** | ❌ | "性能类问题，**共 5 条**"（同样的过度概括） |
| **reflection** | 3 | 1 | 3760 | 20.9 s | ✅ | "性能与稳定性类问题，**共 4 条**"（自查后改对） |

**v1（工具口径有 bug：`count` 只支持单个子串）**

| 范式 | 现象 | 根因 |
|---|---|---|
| plan-and-solve | 调 `count("加载慢/转圈/卡住/白屏")` 得 **0 条**，随后放弃工具、改用 `all()` 心算 → 答案 5 条（错） | 工具只做单关键词子串匹配，模型写的复合查询直接落空 |
| react | 第 2 步**整段没输出 `Action:` 行**（只有结论）→ 解析失败 → 循环终止，**无答案** | 协议违规：模型忘了保持格式，而我的循环没有"提醒重试"这一步 |
| reflection | 我的提示词写了 `count(keyword)`，模型**把占位符当字面量**照抄 → `count("keyword")` = 0 条 → 它把"0 条"当真事实，围绕"关键词体系不完善"写了一整套建议 | 提示词里的占位符没有换成真实例子 + 工具空结果没有区分"没有数据"和"没匹配上" |

**四条结论**

1. **工具口径决定上限**：v1 三条路线全挂，v2 只有 reflection 通过——差别不在模型也不在范式，而在 `count` 支不支持多关键词 OR、提示词给的是真例子还是占位符。**Agent 的效果上限是工具与协议的工程质量，不是模型选型。**
2. **三种范式的成本差 2.3 倍**：plan-and-solve 6810 token / 34.8 s（计划阶段多写了一轮，计划本身 4 步比实际需要的 3 步多）> reflection 3760 / 20.9 s > react **2959 / 16.5 s**。
3. **只有 reflection 具备"改错"能力**：它的初稿其实也答错（5 条），但自查那一步拿工具数据核对后改成 4 条并给出理由。代价是多一轮调用（+≈800 token、+4 s）。**当答案错误代价高、而核对手段便宜时，reflection 是划算的。**
4. **"过度概括"是三者共同的失败模式**：plan-and-solve 与 react 都把"打开详情页白屏"归进卡顿类 → 5 条。这类误差不是幻觉，而是**分类口径没定义清楚**（与 U2、U4 的结论同源），要修得靠"先冻结口径 + 评测集"，而不是换范式。

> 顺带：Reflection 的自我批评之所以有效，是因为它被要求"只看事实与数字是否站得住"，而且有工具可查——**没有可核对证据的自我批评，只是让模型再说一遍好话**。
