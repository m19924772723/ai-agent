# labs/ch01-workflow-vs-agent —— 同一任务两条路径的实测对比（U2 单元）

## 1. 出处

- 母本：第 1 章《初识智能体》1.4.3「Workflow 和 Agent 的差异」（`references/hello-agents/docs/chapter1/第一章 初识智能体.md`）
- U2 的结论原本只是判断（"字段固定的批处理该用工作流"），这个实验把它变成数字。

## 2. 改了什么 / 为什么

| 项 | 设计 |
|---|---|
| 任务 | 12 条中文用户反馈 → 抽 `类型 / 严重度 / 模块` 三列（正是 U2 反例①的场景） |
| 路径 A 工作流 | 关键词规则写死，纯 Python，无网络 |
| 路径 B Agent | 每条一次 LLM 调用（`deepseek-flash`，temperature=0，要求只输出 JSON） |
| 度量 | 延迟（整批/单条/最慢）、成本（token，来自 usage）、格式稳定性（JSON 成功率）、结果稳定性（同批跑 2 遍，比对两遍是否一致）、与规则的交叉一致率 |
| 补的为什么 | 「工作流便宜、稳定」是常识判断，但这个工作区要求**每个结论都要有实测数字**；顺手把"Agent 的不确定性到底有多大"量出来（这是选型时最常被忽略的一项） |

## 4. 真实输出（2026-09-29 实测，deepseek-flash / 12 条 × 2 遍）

```
任务：12 条反馈 → 类型/严重度/模块  |  模型：deepseek-flash
路径A 工作流 : 整批 0.2 ms（0.02 ms/条）  token 0
路径B Agent  : 整批 70.51 s（2.94 s/条，最慢 17.98 s）
               token 合计 5809（242.0/条），JSON 成功 24/24
结果稳定性   : 两遍完全一致 8/12（工作流恒为 12/12）
与规则交叉一致率: 4/12（参考值，不代表谁更对）
倍率         : 延迟 298030×  成本 0 → 5809 token
```

（两遍分耗时：pass1 42.41 s、pass2 28.11 s；prompt 合计 2470 token、completion 合计 3339 token）

**四条结论**

1. **延迟差 6 个数量级**：规则 0.2 ms/批 vs Agent 2.94 s/条；单条最慢 17.98 s（同一条在两个 pass 里可以差 10 倍以上：最慢 17.98 s / 最快 1.21 s）——排队与推理长度都会影响，用户侧表现为"时快时慢"。
2. **成本从 0 变成 242 token/条**：12 条两遍 = 5809 token。这个量级下，1 万条反馈就是 ~242 万 token。
3. **Agent 的结果不稳定：12 条里 4 条两遍分类不同（33%）**。明细（`out/compare.json`）：
   - #4「列表加载特别慢」：pass1 `体验/中/列表` → pass2 `bug/中/列表`
   - #5「能不能加一个导出 Excel 的按钮」：pass1 模块`其他` → pass2 模块`列表`
   - #11「建议把常用的功能放到首页」：pass1 严重度`中` → pass2 严重度`低`
   - #12「内容列表里的图片加载失败」：pass1 严重度`中` → pass2 严重度`高`
   工作流的答案永远是同一份（12/12 稳定）。
4. **与规则口径交叉一致只有 4/12**，但不代表规则更对：例如 #3「登录一直提示验证码错误」，规则判 `体验/低`，模型判 `bug/高`——**模型的判断其实更合理**。真正的问题是：**字段口径没有先定义清楚**，所以换实现就换结果。产品结论是"先把分类口径冻结，再选实现"，而不是"规则永远对"。

> 一句话：固定字段的批处理用工作流，省的是**延迟、成本，还有"不确定性"**；如果这类任务真的非要用模型，也应该先把口径写进提示词并加离线评测集，否则同一批数据每天都可能得出不同报表。
