# 成果 2026-10-03：三范式同题对比（U6 单元）

> 五要素：做了什么 / 为什么 / 怎么验证的 / 关键输出 / 复现步骤

## 做了什么

把 **ReAct / Plan-and-Solve / Reflection** 三条控制流放在**同一道题、同一批工具**上跑：

- 题目：12 条用户反馈里最主要的问题是哪类？给条数 + 2 条可执行建议（数字必须由工具统计得出）。
- 真值：代码统计得出（崩溃 3 / 卡顿 4 / 需求 3 / 提示缺失 2 → 最主要 = **卡顿 4 条**），不手写。
- 判分：脚本检查最终答案是否出现正确条数与类别词（客观布尔判分）。
- 两轮留档：v1（我的工具口径有 bug，三条路线全挂）→ v2（修好后的真实对比）。

## 为什么

`plan.md` 单元 U6 的验收：① 对比表每格有具体例子；② 三个范式各自的失败模式各举一例。第 4 章 4.4.5 专门讲 Reflection 的"成本收益分析"，正好用数据把它做实。

## 怎么验证的

| 项 | 证据 |
|---|---|
| 判分客观 | 真值由代码统计；判分只认"出现正确条数 + 正确类别词"，不接受"差不多" |
| 三条路线同条件 | 同一模型、同一批工具、同一个 temperature=0、同一题目 |
| 失败可追溯 | 每轮的 raw 轨迹（Thought/Action/工具返回/自我批评）都在 `out/paradigms*.json` |
| 两轮对照 | v1（工具口径 bug）与 v2（修复后）两份证据都留着，能看出差别来自哪里 |
| 环境干净 | 独立 venv（D 盘解释器），密钥从环境变量取 |

## 关键输出（2026-10-03 实测，step-3.7-flash）

**v2（工具修好之后）**

| 范式 | 步数 | 工具调用 | token | 耗时 | 判分 | 答案摘要 |
|---|---|---|---|---|---|---|
| plan-and-solve | 3 | 2 | **6810** | 34.8 s | ❌ | 性能卡顿类，**共 5 条** |
| react | 3 | 2 | **2959** | **16.5 s** | ❌ | 性能类问题，**共 5 条** |
| **reflection** | 3 | 1 | 3760 | 20.9 s | ✅ | 性能与稳定性类，**共 4 条** |

**v1（`count` 只支持单关键词子串 + 提示词占位符被照抄）**

| 范式 | 现象 | 根因 |
|---|---|---|
| plan-and-solve | `count("加载慢/转圈/卡住/白屏")` → 0 条，随后弃用工具改心算 → 5 条（错） | 工具不支持复合查询 |
| react | 第 2 步整段漏写 `Action:` → 循环终止，**无答案** | 协议违规 + 循环无"提醒重试" |
| reflection | `count("keyword")` → 0 条 → 把 0 当真事实，围绕"关键词体系不完善"写整套建议 | 提示词占位符没换成真实例子；空结果未被区分 |

**四条结论**
1. **效果上限是工具与协议的工程质量**：v1 三条全挂、v2 一条通过，差别不在模型。
2. **成本差 2.3 倍**（6810 / 3760 / 2959 token）：简单任务、事实靠一两次工具可得时，ReAct 最划算。
3. **只有 Reflection 会改错**：初稿也错（5 条），自查拿到工具数据后改成 4 条；代价是多一轮 ≈800 token。
4. **共同失败模式是"过度概括"**：把"白屏"算进卡顿 → 5 条。与 U2/U4 同源：口径没冻结，换谁做都漂。
