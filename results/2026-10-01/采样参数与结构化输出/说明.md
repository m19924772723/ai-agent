# 成果 2026-10-01：采样参数与结构化输出（U4 单元）

> 五要素：做了什么 / 为什么 / 怎么验证的 / 关键输出 / 复现步骤

## 做了什么

给「长文 → 结构化 JSON」任务定义 **pydantic schema**（title / key_points / tags / todos），用 5 组配置跑同一篇 216 字文章并逐组强校验：

| run | 配置 | 目的 |
|---|---|---|
| run1 | `max_tokens=64`, temp=0 | 故意压预算，复现截断 |
| run2 | `max_tokens=8192`, temp=0 | 足额预算的正常结果（基准） |
| run3 | `max_tokens=8192`, temp=1.2 | 看高温度对结构化输出的影响 |
| run4 | `max_tokens=64`, temp=0, **流式** | 验证流式能否拿到 `finish_reason` |
| run5 | `max_tokens=8192`, `response_format=json_object` | 验证端点是否支持约束解码、代价如何 |

## 为什么

`plan.md` 单元 U4 的验收：① 两段真实输出并排对比；② 记录 `finish_reason`；③ 能解释"推理 token 与输出 token 共用一个预算"。这也是把"格式不对/返回空"从玄学变成可诊断的一次实验。

## 怎么验证的

| 项 | 证据 |
|---|---|
| 格式对错可判定 | 每组都用 pydantic `model_validate_json` 强校验，失败会打印具体错误（不是"大概不对"） |
| 截断有显式信号 | 5 组的 `finish_reason` 全部记录（`length` / `stop`），流式组也一样 |
| 推理占比可算 | 对比 `completion_tokens` 与可见输出字符数（run2：1423 vs 329 字符） |
| 温度影响可复现 | run2/run3 同预算只差温度，四个字段逐条列出差异 |
| 原始数据 | `labs/ch03-sampling/out/sampling.json`（5 组完整 usage、输出尾部、解析结果） |
| 环境干净 | 独立 venv（D 盘解释器），密钥从环境变量取 |

## 关键输出（2026-10-01 实测，step-3.7-flash，输入 216 字 / prompt 245 token）

| run | finish_reason | pydantic | completion tokens | 可见输出 | 耗时 |
|---|---|---|---|---|---|
| run1 小预算(64) | **length** | ❌ `Invalid JSON: EOF while parsing a value at line 1 column 0` | 64 | **0 字符** | 4.04 s |
| run2 足额(8192) | stop | ✅ | 1423 | 329 字符 | 9.84 s |
| run3 高温(1.2) | stop | ✅（内容漂移） | 1646 | 338 字符 | 10.82 s |
| run4 流式+小预算 | **length**（流式拿到了） | ❌ 同上 | 64 | **0 字符** | 1.84 s |
| run5 json_object | stop | ✅ | **905** | 263 字符 | 9.38 s |

**四条结论**
1. `max_tokens` 是**推理 + 输出**的总预算：64 时全部被推理吃掉，客户端拿到空字符串（不是半句 JSON），`finish_reason=length`。
2. `finish_reason` 是显式截断信号，**流式也能拿到**（最后一块 chunk）→ 关闭 U1 的遗留问题；生产必须把它当错误分支。
3. 温度影响**内容稳定性**而非格式合法性：temp=1.2 时 schema 仍通过，但标题、标签数量（4→3）、待办措辞都变了 → 抽取类任务用 temp=0。
4. `response_format={"type":"json_object"}` 端点支持，且同任务 **省 36% token**（905 vs 1423）→ 结构化抽取默认开。
