# 成果 2026-10-06：评测集与 Judge 一致性（U9 单元）

> 五要素：做了什么 / 为什么 / 怎么验证的 / 关键输出 / 复现步骤

## 做了什么

1. **建 20 条评测集**（`make_dataset.py` → `dataset.json`）：反馈原文 + 人工真值（类型/严重度/模块）+ 4 条边界样本；真值由代码自检（格式与分布）。
2. **两套打分器评同一份预测**（`run_eval.py`）：规则精确匹配 vs LLM-as-judge（逐字段判一致性 + 给理由），两套共用同一份**冻结口径**（数据标注 / 抽取提示词 / 裁判标准三处同源）。
3. **反向探针**（`probe_judge.py`）：故意把 3 条样本的预测改错，验证两套打分器是否真的会报警。
4. 抽取结果缓存（`out/predictions.json`），重跑裁判不重复花钱。

## 为什么

`plan.md` 单元 U9 的验收：① 20 条评测集；② LLM-as-judge 打分；③ 与规则判分的一致性对比（谁更严、差在哪几例）。第 12 章 12.1 讲评估基础、12.4 讲 LLM Judge——本单元把"评估"从 U6 的临时真值判分升级成**可复用的正式评测**。

## 怎么验证的

| 项 | 证据 |
|---|---|
| 评测集可自查 | `self_check()` 校验格式/重复/分布，输出"自检：通过"+ 三维分布 |
| 两套打分器同源 | 数据标注、抽取提示词、裁判标准共用 `RUBRIC_TEXT`，避免"标准漂移"造成的假一致 |
| **一致性有负样本背书** | 注入 3 条错误预测 → 规则 3/3、裁判 3/3 检出，裁判理由准确引用口径 |
| 数字可复现 | 预测缓存 + `--judge-only` 重跑；tokens 逐项记录（抽取 8568 / 裁判 15699 / 探针 15113） |
| 环境干净 | 独立 venv（D 盘解释器），密钥从环境变量取 |

## 关键输出（2026-10-06 实测，step-3.7-flash）

**评测集**：20 条（边界 4 条）｜类型 bug 8 / 体验 7 / 需求 5｜严重度 高 4 / 中 10 / 低 6｜模块 支付 4 / 列表 3 / 登录 3 / 搜索 3 / 内容 4 / 其他 3

| 打分器 | 全对 | 类型 | 严重度 | 模块 |
|---|---|---|---|---|
| 规则判分 | 15/20 | 19/20 | 17/20 | 18/20 |
| LLM 裁判 | 15/20 | 19/20 | 17/20 | 18/20 |

**一致率 20/20（100%）｜严格性差异 0｜tokens 合计 24267**

**反向探针**：注入 3 条错误 → 规则 3/3、裁判 3/3 检出

| 注入 | 裁判理由（摘要） |
|---|---|
| S01 严重度 高→中 | "涉及扣款后订单未生成，涉及资金与数据异常，按口径应为高" |
| S05 类型 需求→体验 | "希望新增搜索按时间排序的能力，属于需求类" |
| S07 模块 内容→其他 | "详情页白屏属于内容模块范畴" |

**模型错在哪（5/20）**：S07 严重度 中→高｜S11 类型+严重度 体验/中→bug/高｜S12 模块 内容→其他｜S18 严重度 高→中｜S20 模块 其他→内容

## 四条结论

1. **一致率必须先被证伪**：100% 一致可能是"裁判只会点头"，注入错误后 3/3 检出才让这个数字成立。
2. **闭集字段用规则判分**：两套结论完全一致，但裁判贵 1.5 万 token/轮、慢约 70 s —— LLM-as-judge 留给规则写不出来的场景。
3. **口径难点在"跨类别"而非"含糊"**：4 条模糊样本全对；错的是 S11 这类"同时像 bug 又像体验"的反馈。
4. **严重度最不稳**（17/20），且错的方向相反 → 需要示例锚点，而不是继续调措辞。
