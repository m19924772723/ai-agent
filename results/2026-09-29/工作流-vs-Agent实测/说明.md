# 成果 2026-09-29：工作流 vs Agent 实测对比（U2 单元）

> 五要素：做了什么 / 为什么 / 怎么验证的 / 关键输出 / 复现步骤

## 做了什么

同一个固定字段抽取任务（12 条用户反馈 → 类型/严重度/模块），用两条路径各跑一遍并量化：
- 路径 A：关键词规则工作流（零 token、纯 Python）
- 路径 B：Agent（每条一次 `deepseek-flash` 调用，temperature=0，要求只输出 JSON），跑 2 遍
采集延迟、token 成本、JSON 成功率、**两遍结果一致性**、与规则的交叉一致率，全部落在 `labs/ch01-workflow-vs-agent/out/compare.json`。

## 为什么

U2 的结论（"字段固定的批处理该用工作流而不是 Agent"）原本只是判断；按本工作区纪律，**结论必须有实测数字**。顺带把"Agent 的不确定性有多大"量出来——这是选型时最常被忽略的一项。

## 怎么验证的

| 项 | 证据 |
|---|---|
| 两条路径都真跑 | 终端输出 + `out/compare.json`（含 24 次调用的逐条原始输出、token、延迟） |
| 数字不是估的 | token 来自 API `usage` 字段；延迟用 `time.perf_counter()` |
| 稳定性不是感觉 | 同批输入跑 2 遍，逐条比对；4 条不一致的明细可点开 JSON 核对 |
| 环境干净 | 独立 venv（D 盘解释器），未污染系统 Python；密钥从环境变量取，未写入文件 |

## 关键输出（2026-09-29 实测）

| 指标 | 工作流（规则） | Agent（deepseek-flash，12 条 ×2 遍） |
|---|---|---|
| 整批延迟 | **0.2 ms** | **70.51 s**（2.94 s/条；单条最慢 17.98 s、最快 1.21 s） |
| 成本 | **0 token** | **5809 token**（242.0/条） |
| 格式成功率 | —（结构由代码保证） | 24/24 JSON 可解析 |
| 结果稳定性 | **12/12**（两遍必然相同） | **8/12**（4 条两遍分类不同，33% 漂移） |
| 与规则口径一致 | 基准 | 4/12（参考值） |

**两个产品级结论**：
1. 省下来的不只是钱和时间，还有**不确定性**——33% 的条目同一输入两次跑出不同分类，直接意味着"每天的报表可能不一样"。
2. 与规则只有 4/12 一致，但**不是规则更对**（例：#3「登录验证码一直错」规则判"体验/低"，模型判"bug/高"，模型更合理）。真问题是**分类口径没先定义清楚**：口径不冻结，换实现就换结果。
