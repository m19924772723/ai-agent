## 2. 核心概念（A/B 设计要点）

1. **A/B 要有"被测试的问题"**：不是随便比两版提示词，而是带着 U9 的结论（严重度最不稳、错误方向相反 → 需要锚点）来验证"加锚点是否真的改善"。
2. **控制变量**：两版只差"严重度示例锚点"一处；模型、温度（0）、数据集、判分逻辑完全相同——否则说不清赢在哪。
3. **判分与 U9 同源**：复用规则判分（精确匹配真值），不引入新的判分器——保证 A/B 结果与 U9 基线可比。
4. **样本量要够读**：20 条（U9 全量）——字段级正确率变化 1 条 = 5 个百分点，足够看出趋势；但结论要标注"20 条小样本"的局限。


**结论（带诚实边界）**：few-shot 锚点在 20 条小样本上让严重度 15/20→19/20、全对 12→15，方向正面但不统计显著（p=0.375）。类型/模块不受影响。
**本单元最重要的收获**：promptfoo 首跑 **40 次调用全 error**——因为 step-3.7-flash 把 `Thinking: ...` 推理文本写进输出 content（system/user 分离时偶发，全部塞 user 消息时必现）。这修正了 U9 的一个盲区：U9 当时 temperature=0 + system/user 分离所以侥幸全解析成功，换成单一 user 消息就现原形。**推理模型的结构化输出必须容错解析 + 提示词尽量放 system。**

## 踩坑（promptfoo 0.124 + stepfun 实测）
1. **v3 results.json 格式**：`results` 是 dict；真实输出在 `response.output`，不在顶层 `output`；`prompt` 是字符串
2. **transform 失败 = 输出丢失**：promptfoo 在 transform 抛错时不保存原始输出（results.json 里只有 error），必须保证 transform 不抛或干脆不设 transform、Python 侧解析
3. **--no-cache 是必须的**：缓存会带回"空 output 的失败结果"（latency/token 有、output 无），给假成功
4. npm 装 promptfoo 在 npmmirror 下 12 分钟：加 `--no-audit --no-fund` 先装、再补 optional（libsql）比一次装完快
