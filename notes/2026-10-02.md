## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **ReAct 的本质是"把外部事实变成观察再喂回模型"**：模型不知道今天几号，但只要给它 `now()` 和 `calculate()` 两个工具，它就能把"实时事实 + 算术"拆成三步完成——**所以** Agent 与 Chatbot 的分野不是模型更强，而是有没有"取事实 → 算 → 收尾"的回路。
2. **失败大多在协议解析层，不在模型层**：同一个问题三次跑，模型逻辑都对，挂掉的是我的正则（不支持 `name="值"`）和跨行捕获——**所以**调试 ReAct 的第一步应该是打印原始输出、检查解析，而不是换模型。
3. **模型会自导自演 Observation**：v2 那次它一次输出里同时写了 `Action:` 和伪造的 `Observation:`——**所以**工程上"观察"只认自己执行工具的结果，模型写的同类字段必须丢弃，否则等于让它自己给自己编证据。
4. **没有工具时，模型会"自信地算错"**：对照组只花 687 token（1/5 成本）却给出 17472 小时（正确值 109.5 小时）——**所以**"省 token"不能脱离"准不准"单独看，错误答案的代价是用户信任。
5. **协议写得稳，比换更强的模型便宜**：v1（无效重试 3 次）4688 token → v3（干净）3181 token，省 47%，模型一个没换。

## 4. 能讲给面试官的一段话（3–6 句，含取舍与数字）

> "我自己手写过一次 ReAct 循环，最有价值的不是它跑通了，而是它坏了三次。
> 模型本身三次都算对了逻辑：先调 `now()` 拿时间、再 `calculate()` 算小时数、再换算成天。挂掉的是我的解析层——第一次不支持 `name="值"` 的参数写法，第二次正则跨行把模型**自己编的 Observation** 也吃进去了。修完这两处，同一个任务的 token 从 4688 降到 3181，模型一个没换，省 47%。
> 这让我得到一个工程结论：ReAct 的失败大多在协议解析层，不在模型层；调试顺序应该是先打印原始输出，再怀疑模型。
> 另外我留了个对照组：同样的任务用一次提示词直接要 JSON，只花 687 token，但答案是错的（说 17472 小时，实际 109.5 小时）——便宜但错，对用户来说更贵。"
