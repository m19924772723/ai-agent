## 2. 核心概念（3–5 条，每条能回答「所以呢」）

1. **框架托管与裸 SDK 是同一批工具的两套玩法**：U3 我手写解析 tool_call JSON、自己执行、自己回填；U15 注册进框架后，循环/回填/失败熔断全由框架接管——**所以**"自己写一遍"和"用框架跑一遍"都要做，才知道框架替你做了什么（U7 的延续）。
2. **框架 1.0.0 对函数工具是 `func(input_text)` 位置式传参**：零参函数必炸 `takes 0 positional arguments`——**所以**接入框架的工具要按签名自适应（tool_adapter），这是框架与"常规函数"之间的 API 缝隙（U8 LLMResponse 同源问题）。
3. **"答案对、工具错"是最隐蔽的失败**：第一版 get_current_time 失败，但最终答案的时间是从 hours_until 成功结果里间接凑出来的——**所以**验证 Agent 要看 trace 逐工具核对，不能只看最终回答。
4. **证据源在 trace 不在 history**：`get_history()` 只留最终对话；中间工具调用在框架自带的 trace（字段叫 `event` 不是 `type`，写盘有缓冲）——**所以**做"日志证明"时先确认数据源在哪，别对着 history 找。
5. **框架自动增强 system prompt**：注册的工具描述自动拼进首轮 prompt（1614 token），模型在同一轮并行发起 3 个 tool_call——**所以**工具描述就是"模型的选择依据"，描述要写清参数与用途。

trace 提取的工具调用证据：step1 并行 3 个 tool_call（get_current_time/calculate/hours_until），
结果全成功（时间 13:26:32、2664、490.56 小时），step2 汇总。工具全部成功 = True。

**踩坑**：① 框架零参函数兼容（tool_adapter 修复）；② 第一版"答案对但 get_current_time 实际失败"——时间是从 hours_until 结果里间接拿的，只盯最终答案发现不了；③ 证据在 trace（event 字段）不在 history；④ trace 写盘缓冲，读前 sleep 0.5s。
