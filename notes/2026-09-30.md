## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **工具调用的最小闭环是四步，不是一步**：模型输出 tool_call → 代码执行工具 → 把结果作为 tool 消息回填 → 再让模型继续；**所以**"工具调用"不是模型自己会查时间，而是我给了它一张表 + 一条回路。
2. **两条实现路线的差别在"契约由谁保证"**：原生 function calling 把工具 schema 交给框架、参数以 JSON 字符串返回，解析交给 SDK；母本风格把格式写进提示词、靠正则硬解——**所以**生产环境用前者，后者只当兜底（正则的成功依赖模型每次都写引号，属于"运气"不是保障）。
3. **多轮的真正含义是"依赖链"**：本次三轮调用是 拿时间 → 算间隔 → 乘法，第二步的参数里带着第一步的结果；**所以**设计实验任务时必须让后一步依赖前一步，否则模型一轮猜完，测不出多轮。
4. **算数交给代码，模型只决定算哪个式子**：`calculate` 用 `ast` 白名单求值，比让模型自己算更可靠；**所以**工具设计原则是"确定性计算外置、判断留给模型"。
5. **成本随轮数线性上涨**：三次调用 2489 token，因为每轮都要重发历史（含工具返回）；**所以** Agent 的成本预算要按"轮数 × 上下文长度"来算，不是按问答次数。

**踩坑**：一开始想把母本的两个工具直接换成"自写的天气工具"，但那样还是得联网（要么抓网页要么调接口），无法满足"无外部依赖"。
怎么试的：改用本机就能拿到、且结果可复现的量——时间、时间间隔、算术。
结果：三条工具全本地、零 key、零网络；同一任务重跑两次（native/prompt）结果一致（1097.95），证明任务本身可复现。

**顺带发现**：母本的正则解析这次没出错，但它成立的前提是"模型每次都写双引号和括号"；我手写 `re.findall(r'(\w+)\s*=\s*"([^"]*)"')` 时就想到了——模型只要写成 `target=2026-10-07 00:00`（无引号），参数就会静默丢掉，工具收到空参报错。这类"契约靠自觉"的写法在生产里是隐患。

## 4. 能讲给面试官的一段话（3–6 句，含取舍与数字）

> "Agent 和 Chatbot 的分水岭是能不能调工具，而工具调用最容易踩的坑是'参数解析'。
> 我把同一个任务用两条路各跑了一遍：OpenAI 原生 function calling 是 3 次调用 / 2489 token / 8.16 秒，参数是结构化 JSON，交给 SDK 解析；把格式写进提示词再自己写正则（教程里的经典写法）是 3 次调用 / 3051 token / 11.29 秒，慢 28%、贵 18%，而且它的正确性依赖模型每次都规规矩矩写引号——我的正则碰到 `target=2026-10-07 00:00` 这种写法就会静默丢参。
> 所以我的取舍是：生产用原生工具调用，提示词解析只当兜底；另外把算术这类确定性计算做成带白名单的工具（我用 `ast` 校验），让模型只负责决定算哪个式子，不让它心算。
> 还有一个容易被忽略的点：三次调用烧掉近 2500 token，因为每轮都要重发历史——多轮 Agent 的成本要按'轮数 × 上下文长度'估，而不是按对话次数。"
