## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **三范式的差别是"控制流"，不是"智能程度"**：同一批工具、同一个模型，Plan-and-Solve 先规划再执行、ReAct 边走边想、Reflection 先做再改——**所以**选范式其实是选"什么时候花 token 换准确率"。
2. **效果上限由工具与协议决定，不由模型决定**：第一轮三条路线全挂，根因是我的 `count` 只支持单关键词子串、提示词里的 `count(keyword)` 被模型当字面量照抄——**所以**"工具口径 + 提示词示例"这两件事的优先级，高于换更强的模型。
3. **只有 Reflection 带"改错"环节，且它必须能查到真证据**：它的初稿同样答错（5 条），自查拿到工具数据后改对（4 条）；**所以**自我批评若没有可核对的事实，只会让模型再说一遍好话（第一轮 `count("keyword")` 得 0 条时，它围绕假事实写了一整套建议）。
4. **成本差 2.3 倍**：plan-and-solve 6810 token / 34.8 s，reflection 3760 / 20.9 s，react 2959 / 16.5 s——**所以**任务简单、事实靠一两次工具就能拿到时，ReAct 性价比最高；错误代价高时才值得上 Reflection。
5. **"过度概括"是共同失败模式**：plan-and-solve 与 react 都把"打开详情页白屏"算进卡顿 → 5 条（真值 4）——**所以**分类类任务的第一件事是冻结口径（和 U2/U4 同源教训）。

**踩坑（今天的主菜：我自己的工具口径把三条路线全带沟里了）**

| 版本 | 现象 | 怎么试的 | 结果 |
|---|---|---|---|
| v1 | plan-and-solve 调 `count("加载慢/转圈/卡住/白屏")` 得 **0 条**；reflection 调 `count("keyword")` 得 **0 条**并围绕"关键词体系不完善"写出整套建议；react 第 2 步漏写 `Action:` 行直接终止、无答案 | 把三条路线每轮的 raw 轨迹逐条打印出来对比，发现两处共同点：① `count` 只做单关键词子串匹配；② 我的提示词里写的 `count(keyword)` 是**占位符**，模型照抄当字面量 | 改两处：`count` 支持多关键词 OR（`count("慢,卡,转圈")`）+ 提示词改成真实例子并注明"不要照抄示例" → v2 |
| v2 | 三条路线都拿到真实统计，reflection 自查后答对 | — | 见上表 |

**关键领悟**：`count("keyword") = 0 条` 这种"空结果"最危险——模型不会说"我查错了"，而是**把 0 当真事实**，然后为不存在的问题生成自洽建议。工程上必须让工具区分"没有匹配"和"查询本身有问题"，或者让工具回传命中的原文片段（本次 v2 就顺带回了 `[类别] 原文`）。

## 4. 能讲给面试官的一段话（3–6 句，含取舍与数字）

> "我把 ReAct、Plan-and-Solve、Reflection 三个范式放在同一道题上跑了一遍——12 条反馈里找最主要的问题、给条数、给建议，答案是 4 条，脚本按真值自动判分。
> 结果是：三条路线的成本差 2.3 倍（6810 / 3760 / 2959 token），但只有 Reflection 答对了——因为它的初稿也错了（5 条，把'白屏'算进卡顿），在'自我批评'那一步用工具数据核对后才改成 4 条。所以我的结论是：简单任务、事实一两次调用就能拿到时用 ReAct（最省最快）；错误代价高、又有便宜核对手段时才值得加 Reflection。
> 更值得说的是另一件事：第一轮三条路线**全挂**，根因不在模型也不在范式，而在我的工具——`count` 只支持单个关键词，模型写 `count("加载慢/转圈")` 直接得 0；而且我的提示词把 `count(keyword)` 写成了占位符，模型照抄成字面量，于是它拿到'0 条'，还围绕这个假事实写了一套完整的改进建议。
> 这教给我两条工程纪律：**Agent 的效果上限是工具与协议的工程质量**；工具返回空结果时必须能区分'没匹配'和'查错了'，否则模型会把空结果当真事实。"
