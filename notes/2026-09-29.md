## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **流式的价值不在首字，在长答案的后续等待**：实测 TTFT 5.387 s / 总耗时 5.454 s，可见 token 几乎全部在最后一段到达——对推理模型，流式省不下首字前的推理时间，所以"用户等了 5 秒"只能靠别的手段解决（进度提示、先给大纲、或换更快模型）。
2. **推理 token 和输出 token 共用一个预算**：stepfun 68 个汉字记账 280 completion tokens，差额是没下发的推理；**所以** `max_tokens` 给太小会把 JSON 断在半句（L1 踩过的坑，这次找到了机理）。
3. **TTFT 是端到端指标，不是模型指标**：同一提示词两家端点 TTFT 差近一倍（5.39 s vs 2.80 s），而业务代码一行没改——**所以**「换模型/换网关」必须走配置，不能散落在代码里。
4. **stream_options={"include_usage": true} 不是所有网关都认**：脚本必须能降级（退回一次非流式调用取用量），否则一个网关差异就把评测脚本打挂。
5. **delta 片段数可以当"真流式"的体检指标**：11 / 31 个片段说明真的是分段到达；如果只有 1 个片段，就是网关把整包下发，客户端感受不到流式。

**踩坑**：第一版把 TTFT 也算成 5.14 s（== 总耗时），一度以为脚本记错时间戳。
怎么试的：改成记录每个 delta 的到达时刻，打印片段数与最大间隔。
结果：`delta_count=11`、最大间隔 58 ms → 不是 bug，是**响应后段批量到达**；脚本如实记录，结论要按这个事实讲。

**环境踩坑**：`uv venv --python 3.11` 默认会把解释器下载到 `C:\Users\1\AppData\Roaming\uv\python`（C 盘）。
怎么试的：先查 `UV_PYTHON_INSTALL_DIR` 未设置，再看 `uv python list` 里已有的解释器全在 C 盘。
结果：设 `UV_PYTHON_INSTALL_DIR=D:\code\environment\uv\python` 后重建 venv，解释器落在 D 盘（`D:\code\environment\uv\python\cpython-3.11.16-...`）。

## 4. 能讲给面试官的一段话（3–6 句，含取舍与数字）

> "做 Agent 前端时我把流式调用当默认，但我先量了一遍再下结论：同一提示词下 stepfun 首字 5.39 秒、deepseek 2.80 秒，而可见 token 几乎是在最后一段批量到达的——说明首字延迟主要来自推理阶段，流式并不能救首字，能救的是长答案的后续等待。
> 另外我们端点的 completion_tokens 记账远大于可见输出（68 汉字记账 280），差值是没下发的推理 token，这正好解释了我们 L1 项目里'JSON 断在半句'的根因：推理和输出共用同一个 max_tokens 预算。
> 这两条直接改了我的产品决策：界面给进度反馈而不是假装在打字，以及把 max_tokens 从 512 提到 8192 并把 finish_reason 当显式截断信号。"
