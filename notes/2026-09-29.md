## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **流式的价值不在首字，在长答案的后续等待**：实测 TTFT 5.387 s / 总耗时 5.454 s，可见 token 几乎全部在最后一段到达——对推理模型，流式省不下首字前的推理时间，**所以**「用户等了 5 秒」只能靠别的手段解决（进度提示、先给大纲、或换更快模型）。
2. **推理 token 和输出 token 共用一个预算**：stepfun 68 个汉字记账 280 completion tokens，差额是没下发的推理；**所以** `max_tokens` 给太小会把 JSON 断在半句（这次终于搞清了机理，不再只是"踩过坑"）。
3. **TTFT 是端到端指标，不是模型指标**：同一提示词两家端点 TTFT 差近一倍（5.39 s vs 2.80 s），而业务代码一行没改——**所以**「换模型/换网关」必须走配置，不能散落在代码里。
4. **`stream_options={"include_usage": true}` 不是所有网关都认**：脚本必须能降级（退回一次非流式调用取用量），否则一个网关差异就把评测脚本打挂。
5. **delta 片段数可以当"真流式"的体检指标**：11 / 31 个片段说明真的是分段到达；如果只有 1 个片段，就是网关把整包下发，客户端感受不到流式。

# 追加单元 U2（09-29 同日完成，原排 09-30）· Agent 与工作流的边界

> 计划依据：`plan.md` 单元 U2 ｜ 材料：母本 `docs/chapter1/第一章 初识智能体.md`（1.1.2 / 1.1.3 / 1.2 / 1.4.3 / 1.5）

## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **现代 Agent = 让 LLM 当大脑的循环系统**：感知 → 思考（规划 + 工具选择）→ 行动 → 观察，落地形式就是 `Thought / Action / Observation` 这套交互协议；**所以**它和"一次提示词出结果"的区别不是模型变强了，而是多了"根据反馈重来一轮"的机制。
2. **Workflow 与 Agent 的分界线是自由度**：工作流把路径预先编排死（本质是一张静态流程图），Agent 只拿到目标、路径自己定——书里那句"没有写死的 `if 天气=晴 then 推荐颐和园`"就是判据；**所以**选型第一问永远是"这条路径能不能提前枚举"。
3. **LLM Agent 是神经符号混合体**：内核是神经网络（处理模糊自然语言），中途产物是符号（计划、工具调用、结构化参数）——**所以**它既能接住模糊需求，又能被解析器/校验器约束住，不会完全失控。
4. **任务环境决定设计，不能省**：LLM Agent 面对的环境通常**部分可观察、随机、多行动者、序贯且动态**；**所以**记忆、不确定性处理、快速闭环这三件事是设计必选项，而不是优化项。
5. **自主性是有代价的**：反应式智能体快但短视，规划式智能体强但贵，现代 LLM Agent 用"规划-反应"微循环折中——**所以**产品上"要不要上 Agent"同时是一道成本与延迟的预算题。

## 3. 动手记录（本次是判断练习，产出＝下面两段文字）

### 3.1 300 字：一个自动化任务为什么用工作流而不是 Agent

> 以本目录每天真正要做的一件事为例：把 `notes/` 里当天的笔记压成台账、更新 `progress.md`、再提交 git。这件事看着"需要理解"，其实每一步都能提前写死——读哪几个文件、字段摆哪一列、什么时候提交，路径完全可以预先枚举，所以它是**工作流**，不是 Agent。
> 理由三条。一是**确定性**：脚本每次产出的台账格式一样，Agent 每次理解不同、输出就会漂。二是**成本与延迟**：脚本零 token、毫秒级；Agent 每天要花若干次推理调用，慢几十秒还可能失败。三是**可测试**：脚本能写用例、能 diff、能幂等重跑；Agent 的"判断"只能靠人看，回归成本高。
> 什么时候才值得上 Agent：目标能用一句话说清、但**路径说不清**的任务。比如"根据今天的天气推荐一个北京景点"——先查天气，再按晴雨挑室内/室外，再结合用户偏好，分支取决于中间结果，写死的 `if-else` 永远漏情况。这时才把自由度和成本一起接受下来。
> 一句话：**能画出流程图就别上 Agent；画不出来的才交给 Agent。**

（约 330 字）

### 3.2 三个「加 Agent 反而更差」的具体场景

| 场景 | 为什么加了 Agent 更差 |
|---|---|
| **字段固定的批处理**（把 500 条反馈抽成"类型/严重度/模块"三列） | Agent 每条都要一次推理：成本 ×500、延迟不可接受，且格式会漂（同一条两次抽出不同措辞）；工作流里规则 + 小模型就能稳定命中，不中也能定位到哪条规则 |
| **有审计/合规要求的流程**（数据脱敏、发布上线、审批） | Agent 的执行路径不可预期，出问题也无法复盘到"哪一步的规则错了"；工作流每一步都有确定记录，能对账、能回滚 |
| **高频、低价值、失败代价明确的重复任务**（每天几百次的清洗/去重/格式化） | Agent 的方差和单价在这个量级上是浪费；工作流可以幂等重跑、可以设明确的重试与告警策略 |

### 3.3 判断清单（值得上 Agent 的信号）

- 目标能一句话说清，但**步骤说不出**（分支取决于中间结果）
- 输入是非结构化自然语言，规则**写不穷**
- 需要跨多个工具，且工具的**组合方式事先不定**
- 允许较高延迟与 token 成本，并且**失败有人工兜底**
- 反过来（该用工作流）：能画出完整流程图 / 分支可枚举 / 有审计要求 / 高频低价值 / 对延迟敏感

### 3.4 自测：第 1 章习题的四个 case（我的判断，非书里答案）

| case | 是否智能体 | 判断依据 |
|---|---|---|
| A 冯·诺依曼结构超算（2EFlop） | 不是 | 没有感知-行动闭环，也没有任务环境，只是算力；算得快 ≠ 智能体 |
| B 高速上的自动驾驶避障 | 是，**反应式**（含模型式成分） | 毫秒级感知→动作直接映射，几乎不做未来规划；用"时间/反应性"维度定位 |
| C AlphaGo 对弈 | 是，**规划式**（基于目标/效用） | 用内部世界模型推演未来数十步，追求最优解；代价是算力与时间 |
| D ChatGPT 智能客服 | 是，**LLM 智能体 / 混合式** | 既要查订单、分析原因（规划），又要即时安抚情绪（反应）；中间产物是工具调用（符号）→ 神经符号混合 |

## 4. 能讲给面试官的一段话（3–6 句，含取舍与数字）
