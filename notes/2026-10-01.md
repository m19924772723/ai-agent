## 2. 核心概念（3–5 条，每条一句话，要能回答「所以呢」）

1. **`max_tokens` 是"推理 + 输出"的总预算**：给 64 时 token 全被推理吃掉、可见输出 0 字符——**所以**"模型返回空内容""JSON 断在半句"要用"预算不够"解释，而不是"模型不听话"。
2. **`finish_reason` 是显式的截断信号，流式也能拿到**（最后一块 chunk 的 `choices[0].finish_reason`）——**所以**生产代码必须把它当错误分支处理，绝不能靠"JSON 解析失败"去反推。
3. **温度调的是内容稳定性，不是格式合法性**：temp=1.2 时 schema 照样通过，但标题、标签数量、措辞全变了——**所以**抽取/评测/入库类任务必须低温，"结构化输出"不等于"可复现输出"。
4. **约束解码（`response_format=json_object`）同时解决格式和省钱**：同任务 905 token vs 1423 token（-36%）——**所以**结构化抽取默认开它，端点也支持。
5. **推理 token 占大头（run2 里约 82%）**：可见输出 329 字符 ≈ 250 token，其余都是没下发的推理——**所以**上下文与成本预算要按"推理 + 输出"估，这也解释了 U1 的 TTFT≈总耗时。

**踩坑**：原以为"小预算"会得到**半句 JSON**（截在半句），实际拿到的是**完全空的字符串**。
怎么试的：把 5 组配置的输出尾部都打了 160 字，再比对 `completion_tokens` 与可见字符数；run1/run4 的可见输出都是 0 字符，而 `completion_tokens` 正好等于上限 64。
结果：64 个 token 全被**推理**消耗，模型还没开始输出正式内容就被掐断 → 报错文本 `EOF while parsing a value at line 1 column 0` 说的是"空字符串"，不是"半句"。这条把 L1 时期"JSON 断在半句"的经验修正得更准确了：**断与不断取决于推理占比，不一定是"断一半"**。

**顺带解决 U1 遗留项**：流式响应里 `finish_reason` 能拿到（run4 = `length`），位置在最后一个 chunk 的 `choices[0].finish_reason`。当天就回填进 `notes/2026-09-29.md` 的遗留问题。
