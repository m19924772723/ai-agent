## 2. 核心概念（4 条，每条能回答「所以呢」）

1. **依赖链验证要靠自动校验，不能看答案就信**：脚本从 trace 提取 hours_until 返回的小时数，再检查 calculate 参数里是否含这个数（±0.5 内）——**所以**"链条真的发生"是有机器判据的，不是模型说链了就链了。
2. **"工具全对、收尾失败"是 Agent 特有的失败模式**（继 U15 的"答案对、工具错"后第二种）：SimpleAgent 4 次都正确调用了 hours_until→calculate、拿到 66.85，却在最后一步答"抱歉，我无法回答这个问题"——**所以**验证 Agent 必须覆盖"最后一步能不能把结果说出口"。
3. **同一任务换 Agent 类型结果天差地别**：SimpleAgent 拿结果后只用 45 token 就放弃；ReActAgent 会继续"思考→回答"。**所以**"选框架"实际是"选行为"，SimpleAgent 这种"调用型"agent 不适合"必须收尾给结论"的任务。
4. **token 用量暴露放弃信号**：SimpleAgent step3 只有 45 completion token（等于没想就放弃），ReActAgent 收尾 step 明显更长——**所以** trace 里的 token 数是诊断"模型是否摆烂"的快速指标。

## 4. 能讲给面试官的一段话（3–6 句）

> "我做了一个工具调用链的实验：让 agent 先算'到某个日期还有多少小时'，再把那个小时数除以 7——第二个工具的参数必须来自第一个工具的结果。我从框架 trace 里提取完整调用序列自动校验：确实调用了两个工具、参数确实来自前一步、答案与真值一致。
> 但更重要的发现是框架选型：用 SimpleAgent 跑同一任务 4 次，工具链每次都完美——hours_until 返回 467.95，calculate 收到 467.95/7 返回 66.85——可 agent 每次都在最后回答'抱歉我无法回答'，等于它拿到了正确答案却不敢说出口。换成 ReActAgent，一次就给出 66.85。
> 我的结论是：验证 Agent 不能只看工具调没用、也不能只看最终答案对不对，要覆盖'能不能把结果收尾成答案'这一环；而且选框架本质是选行为——SimpleAgent 是调用型、ReActAgent 是推理型，任务需要哪种行为就选哪种，不是哪个'更好'。"
